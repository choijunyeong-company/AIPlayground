# Skill flow

1. 해당 작업과 관련된 두레이 업무를 조회하여 작업 사항이 무엇인지 파악합니다. [참조](#두레이-업무-내용-조회)
2. 현재 브렌치에서 작업한 내역을 확인합니다. [참조](#브렌치-작업-내역-파악)
3. 1, 2번으로 파악한 컨텍스트를 기반으로 풀리퀘스트 본문을 구성합니다. [참조](#pull-request-본문-작성-가이드)
4. 현재 브렌치를 병합하는 풀리퀘스트를 생성합니다. [참조](#풀리퀘스트-생성)

# 두레이 업무 내용 조회

## 1. 프로젝트 코드 획득

`basename "$PWD"` 명령을 실행하여 현재 작업 디렉토리의 이름(cwd)을 확인합니다.
다음 경로의 파일에서 두레이 프로젝트 정보가 있는지 확인합니다. (경로 마지막의 `{cwd}`는 디렉토리가 아닌 파일명입니다.)
`~/.agent-memory/dooray-project-info/{cwd}`

해당 파일에는 아래와 같은 정보가 존재합니다.
```
project_code=""
```
해당 파일 혹은 내부 컨텐츠를 확인할 수 없는 경우, 사용자에게 입력을 요청합니다.
전달받은 입력을 해당 파일에 기록합니다. 파일이 기존에 존재하지 않는 경우 파일을 생성 후 기록합니다.

## 2. 업무 번호 획득

현재 브렌치의 이름을 읽습니다. 브렌치 명은 suffix로 업무 식별 번호를 가집니다.
브렌치 이름에서 마지막 `/` 뒤에 오는 숫자를 업무 번호로 사용합니다.
```
feature/111 : 업무번호 111번
feature/.../1830 : 업무번호 1830번
```

## 3. 업무 조회

두레이 mcp를 사용하여 업무 내용을 조회합니다.
업무 조회 시 획득한 프로젝트 코드와 업무 번호를 사용합니다.

# 브렌치 작업 내역 파악

## 1. 기준 커밋 Sha 도출

`BASE=$(git merge-base <current-branch> <base-branch>)`
해당 명령을 통해 현재 브렌치가 파생된 커밋의 해쉬를 획득합니다.
예시: `BASE=$(git merge-base HEAD develop)`

base-branch는 다음 우선순위로 결정합니다.
1. 사용자가 프롬프트에서 특정 브렌치를 base로 명시한 경우, 해당 브렌치를 사용합니다.
2. 그렇지 않은 경우 `develop` 로컬 브렌치를 기본값으로 사용합니다.
3. `develop`을 찾을 수 없는 경우 사용자에게 base-branch 입력을 요청합니다.

## 2. diff 파악

`git diff "$BASE"...HEAD`
해당 명령을 실행하여, 기준 커밋부터 HEAD까지의 변경사항을 파악합니다.

# Pull request 본문 작성 가이드

1. `{프로젝트 루트}/.github/pull_request_template.md` 경로에 템플릿 파일이 존재하는지 확인합니다.
2. 템플릿 파일이 존재한다면, 해당 템플릿의 목차를 반드시 준수합니다.
3. 템플릿 파일이 별도로 존재하지 않는다면, 아래 형식을 따릅니다.

```
## 개요

간략한 요약문을 작성합니다.

## 변경 사항

변경사항들 중 리뷰어가 주목할 만한 내용을 강조합니다.

## 리뷰어 요청사항

어떤 부분을 중점적으로 리뷰해야 하는지에 대한 가이드입니다. 사용자의 특정 지시가 없다면 "코드 가독성 확인 부탁드립니다."로 작성합니다.
```

## 본문 작성 스타일

- 본문을 읽는 사람은 3년차 이상의 개발자로 설정합니다. 해당 연차에 맞는 기술 용어를 사용합니다.
- 정중한 톤으로 문장을 작성합니다. "~함"과 같은 반말을 사용하지 않고, "~했습니다.", "~고려 부탁드립니다." 등 리뷰어에 대한 존중을 문장에 담습니다.
- 기존 프로젝트의 일관성을 지킬 수 없었던 부분이 있다면, 그 이유를 간략하게 언급하고 `리뷰어 요청사항` 섹션에 기재합니다.
- PR 목적에서 벗어나는 부수적인 변경사항은 `상황-행동-결과` 형식으로 명확히 설명합니다.
    (예시: "이번 PR의 목적과는 무관하게 A 부분에서 문제를 발견하여 B와 같은 조치를 취했습니다. D, E에 영향을 미쳤으나 정상 동작을 확인했습니다.")

## 본문 작성 시 하면 안 되는 것

- 변경이 발생한 파일들의 이름 및 경로를 단순히 나열하지 않습니다.
- 리뷰어에게 반드시 알려야 할 코드 변경사항의 경우, 코드가 3줄 이하라면 코드 블록으로 본문에 직접 포함하고, 그 이상이라면 파일명을 기술하여 확인을 요청합니다.
- 마크업 문법 및 이모티콘 사용을 최대한 지양합니다.
- 생성한 본문에 'Generated with Claude'와 같은 AI 에이전트 시그니처를 부착하지 않습니다.

# 풀리퀘스트 생성

기준 브렌치로 병합을 요청하는 풀리퀘스트를 생성합니다.
아래 지침을 반드시 준수합니다.
- Merge commit을 생성하는 병합 방식을 선택합니다.
- PR Assignee를 현재 사용자(`git config user.name`으로 확인)로 설정합니다.

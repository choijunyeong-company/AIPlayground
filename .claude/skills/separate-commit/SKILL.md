변경사항을 의미 단위로 나누어 여러 개의 커밋을 만드는 스킬입니다.

## 핵심 제약 (절대 위반 금지)

- **각 커밋은 cherry-pick 가능해야 합니다.**
- **cherry-pick 가능하다 = 그 커밋 하나만 적용해도 빌드가 성공해야 합니다.**
- 따라서 인터페이스 변경에 대한 사용처 수정이 누락된 형태의 분할은 절대 금지합니다.
- 사용자 환경의 git hook(pre-commit, commit-msg 등)을 절대 우회하지 마십시오. `--no-verify`, `--no-gpg-sign` 등의 플래그 사용 금지. hook이 실패하면 원인을 파악해 수정한 뒤 새 커밋을 만듭니다.

## 절차

### Step 1: 변경 내역 전수 확인

다음 명령으로 변경된 내용을 빠짐없이 파악합니다.

```bash
git status
git diff HEAD
```

`git diff HEAD`로 스테이지/언스테이지된 모든 변경을 함께 확인합니다.

### Step 2: 세션 컨텍스트와 변경 내역 분석

지금까지의 세션 대화와 실제 변경된 코드를 함께 분석하여 작업의 의도(어떤 기능을 추가했는지, 어떤 버그를 고쳤는지, 어떤 리팩터링을 했는지)를 파악합니다.

### Step 3: 의도가 불명확하면 사용자에게 확인

분석만으로 의도를 명확히 파악할 수 없는 경우(예: 여러 작업이 섞여 있어 구분이 모호한 경우), 사용자에게 의도를 직접 물어봅니다.

### Step 4: 커밋 템플릿 확인 또는 생성

현재 작업 디렉터리 이름을 얻은 뒤, `~/.commitTemplates/{cwd이름}.md` 경로의 템플릿 파일 존재 여부를 확인합니다.

- **존재하는 경우**: 파일을 읽어 커밋 메시지 형식을 파악합니다.
- **존재하지 않는 경우**: `init-commit-template` 스킬을 Skill 툴로 호출하여 템플릿을 생성합니다.

```
Skill 툴 호출 예시:
  skill: init-commit-template
```

생성된 템플릿을 읽어 이후 커밋 메시지에 적용합니다.

### Step 5: 변경사항을 의미 단위로 분할

다음 단계 규칙에 따라 변경사항을 묶음으로 분류합니다.

#### 단계1: 공유 객체 변경

- 여러 곳에서 사용되는 공통 객체(공유 유틸, 공유 타입, 공유 컴포넌트 등)가 수정된 경우, 해당 객체의 변경사항만으로 하나의 커밋을 만듭니다.
- 보통 파일 1~3개 수준입니다.
- 단, 이 변경이 인터페이스 변경을 동반한다면 단계3의 규칙을 적용합니다(아래 참고).

#### 단계2: 비공유 객체 변경 묶음

- 사용처가 많지 않고 영향 범위가 미미한 객체들의 변경은 다수를 하나의 커밋으로 묶을 수 있습니다.
- 너무 자잘한 변경을 별개의 커밋으로 쪼개지 마십시오.

#### 단계3: 인터페이스 변화

- 인터페이스(함수 시그니처, 공개 API, 타입 정의 등)가 변경되어 사용처 코드 수정을 유발한 경우, **파일 수와 무관하게 인터페이스 변경과 그 사용처 변경을 하나의 커밋으로 묶어야 합니다.**
- 인터페이스만 바꾸고 사용처 수정을 다음 커밋으로 미루면 그 커밋은 빌드에 실패합니다. 즉 cherry-pick 불가능합니다. **절대 금지합니다.**

### Step 6: 분할 계획 사전 승인 (안전 장치)

실제 `git add`/`git commit`을 실행하기 **전에**, 분할 계획을 사용자에게 먼저 보여주고 승인을 받습니다.

다음과 같은 형식으로 제시합니다.

```
[분할 계획]
  커밋 1: <메시지 요약> — 파일: <files>
  커밋 2: <메시지 요약> — 파일: <files>
  ...
이 계획대로 진행할까요?
```

사용자가 수정을 요구하면 계획을 다시 짭니다. 승인을 받기 전에는 커밋을 만들지 않습니다.

### Step 7: 묶음별로 스테이징 및 커밋

승인된 분할 계획에 따라 각 묶음을 순서대로 처리합니다.

각 묶음에 대해:

1. 해당 묶음에 속한 파일들만 명시적으로 스테이징합니다.
   ```bash
   git add <files>
   ```
   `git add .`이나 `git add -A`로 광범위 스테이징하지 마십시오.

2. Step 4에서 파악한 템플릿 형식에 맞춘 커밋 메시지로 커밋합니다.
   ```bash
   git commit -m "..."
   ```
   hook을 우회하는 플래그(`--no-verify` 등)는 절대 사용하지 않습니다.

3. **각 커밋이 그 자체로 유효(빌드 성공)함을 확인합니다.** 인터페이스 변경에 사용처 수정이 누락되어 있지 않은지 점검합니다. 필요하다면 빌드/테스트를 실행해 검증합니다.

### Step 8: 결과 보고

모든 분할 커밋이 완료된 후 다음 명령으로 결과를 확인하고 사용자에게 보고합니다.

```bash
git log --oneline -n {커밋수}
```

생성된 커밋 목록을 사용자에게 제시하고 작업을 종료합니다.

## 체크리스트 요약

- [ ] `git status`, `git diff HEAD`로 변경 전수 확인
- [ ] 의도 파악(필요 시 사용자에게 질문)
- [ ] 커밋 템플릿 확인/생성(`init-commit-template` Skill 호출)
- [ ] 단계1/2/3 규칙으로 의미 단위 분할
- [ ] 분할 계획 사용자 승인
- [ ] 묶음별 스테이징 → 커밋 (hook 우회 금지)
- [ ] 각 커밋이 cherry-pick 가능(빌드 성공)함을 확인
- [ ] `git log --oneline -n {N}`로 결과 보고

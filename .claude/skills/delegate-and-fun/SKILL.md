# delegate-and-fun

## 개요

사용자가 긴 프롬프트(500자 이상)로 여러 작업을 한 번에 전달한 경우, 작업을 분해하여 명세 파일과 체크리스트 파일을 생성하고, 클로드 팀(혹은 폴백으로 Agent 툴 워커)을 통해 순차/병렬로 실행 및 검증하는 워크플로우를 제공합니다.

## 활성화 검토

- 사용자 프롬프트가 **500자 이상**이고, 다수의 독립적인 작업이 식별되는 경우 본 스킬을 활성화합니다.
- 단일 작업이거나, 단순 질의/대화 성격이라면 활성화하지 않습니다.

## 디렉토리 구조

```
delegate-and-fun/
├── SKILL.md
├── taskdetail/
│   └── {프로젝트명}_{작업명}.md   # 작업 명세
└── taskchecklist/
    └── {프로젝트명}_{작업명}.md   # 체크리스트
```

- `{프로젝트명}`: 현재 작업 디렉토리명 (`basename "$(git rev-parse --show-toplevel 2>/dev/null || pwd)"`)
- `{작업명}`: 프롬프트의 핵심 주제로부터 클로드가 도출. 일관된 명을 도출하기 어려우면 사용자에게 입력 요청
- 명세 파일과 체크리스트 파일은 **동일한 파일명**을 사용합니다.

# 플로우 1: 입력 형식 확인 및 명세 파일 생성

1. 프롬프트 분석 후 `{프로젝트명}_{작업명}` 도출.
   - 작업명이 명확하지 않으면 사용자에게 입력을 요청합니다.
2. `taskdetail/{프로젝트명}_{작업명}.md` 파일을 다음 포맷으로 작성합니다.

```md
# 작업개요

(전체 작업의 목적과 범위 요약)

# Task1: 작업1 제목

(작업1 상세 명세)

# Task2: 작업2 제목
- dependencies: [Task1]

(작업2 상세 명세. dependencies 필드가 있는 작업은 병렬처리 불가)

# Task3: 작업3 제목

(작업3 상세 명세)
```

**규칙**
- 작업 식별자는 `Task1`, `Task2`, ... 의 순차 번호 형식.
- `dependencies` 필드는 단일/다중 모두 배열 형식으로 통일 (`[Task1]`, `[Task1, Task2]`).
- `dependencies` 필드가 없는 작업은 다른 작업과 병렬 실행 가능.

3. 명세 파일 작성 후 **사용자에게 검토 및 승인을 요청**합니다. 승인 전까지 후속 플로우로 진입하지 않습니다.

# 플로우 2: 클로드 팀 활성화 여부 확인

다음 순서로 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 환경변수의 활성화 여부를 확인합니다.

1. `{프로젝트 루트}/.claude/settings.json`
2. `{프로젝트 루트}/.claude/settings.local.json`
3. `~/.claude/settings.json`
4. `~/.claude/settings.local.json`

```json
"env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
}
```

- 위 파일 중 어디에서든 `"1"`로 설정된 경우 → **플로우 3-A (클로드 팀)** 진입.
- 어떤 파일에서도 활성화되지 않은 경우 → **플로우 3-B (폴백)** 진입.

# 플로우 3-A: 클로드 팀 생성 및 실행

## 체크리스트 파일 생성

`taskchecklist/{프로젝트명}_{작업명}.md` 파일을 다음 포맷으로 작성합니다.

```md
- [ ] Task1
- [ ] Task2, dependencies: [Task1]
- [ ] Task3
```

## 팀 구성

다음 두 종류의 에이전트로 팀을 생성합니다.

### 에이전트 1: 리더

**역할**
- 체크리스트 파일을 확인하여 다음으로 실행 가능한 작업(미완료 + 의존성 모두 완료)을 도출.
- 작업 식별자에 해당하는 명세를 `taskdetail/{프로젝트명}_{작업명}.md`에서 조회 (컨텍스트에 이미 명세가 있다면 재조회 불필요).
- 워커에게 **작업 식별자 + 작업 명세**를 전달.
- 워커로부터 완료된 작업 식별자를 수신하면 체크리스트의 해당 항목을 `[x]`로 갱신.
- **동시에 최대 3개의 워커**까지 가동 가능 (병렬 가능 작업이 있을 때).

**체크리스트 갱신 예 (Task1 완료 시)**
```md
- [x] Task1
- [ ] Task2, dependencies: [Task1]
- [ ] Task3
```

### 에이전트 2: 워커

**역할**
- 리더로부터 전달받은 작업 식별자 및 명세를 컨텍스트에 유지.
- 명세대로 작업 수행.
- 작업 완료 후 명세와 결과의 일치 여부를 **자체 재검증**하고 필요 시 개선.
- 검증 완료 후 리더에게 **완료된 작업의 식별자**를 전달.

## 종료 조건

체크리스트의 모든 항목이 `[x]`로 갱신되면 플로우 4로 진입합니다.

# 플로우 3-B: 폴백 모드 (클로드 팀 비활성화 시)

클로드 팀을 사용할 수 없는 경우, **메인 세션이 리더 역할**을 직접 수행하고 `Agent` 툴로 워커를 spawn합니다.

## 체크리스트 파일 생성

플로우 3-A와 동일하게 `taskchecklist/{프로젝트명}_{작업명}.md`를 생성합니다.

## 워커 spawn 규칙

- `subagent_type`: `general-purpose`
- 한 번에 spawn할 작업: 체크리스트에서 미완료 + 의존성 충족된 작업 중 최대 3개.
- 병렬 spawn은 동일 메시지에서 여러 `Agent` 툴 호출로 처리합니다.
- 워커의 프롬프트에는 **작업 식별자와 작업 명세 전문**을 포함합니다.
- 워커에게는 작업 완료 시 **작업 식별자를 명시적으로 결과에 포함하도록** 지시합니다.

## 동기화 및 갱신

- `Agent` 툴 호출의 결과 반환을 **워커 작업 완료 신호**로 간주합니다.
- 결과에서 완료된 작업 식별자를 추출하여 체크리스트의 해당 항목을 `[x]`로 갱신.
- 다시 다음 실행 가능 작업을 선정하여 spawn 반복.

## 종료 조건

체크리스트의 모든 항목이 `[x]`로 갱신되면 플로우 4로 진입합니다.

# 플로우 4: 작업 종료 및 정리

- `taskdetail/{프로젝트명}_{작업명}.md` 와 `taskchecklist/{프로젝트명}_{작업명}.md` 는 **삭제하지 않고 그대로 보존**합니다 (이력 추적용).
- 플로우 3-A로 진행한 경우, **클로드 팀을 해체**합니다.
- 사용자에게 작업 완료 사실과 명세/체크리스트 파일 경로를 보고합니다.

# 빠른 참조

| 단계 | 무엇을 | 어디에 |
|------|--------|--------|
| 명세 도출 | 프롬프트 분석 → `{프로젝트명}_{작업명}` | (네이밍) |
| 명세 파일 | `# 작업개요`, `# Task1`, `# Task2`(dependencies 포함) | `taskdetail/{이름}.md` |
| 사용자 승인 | 명세 검토 후 진행 동의 받기 | (대화) |
| 팀 활성화 확인 | `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` 4개 위치 확인 | (settings.json들) |
| 체크리스트 | `- [ ] Task1` 형식 | `taskchecklist/{이름}.md` |
| 실행 | 팀(리더+워커) 또는 메인+Agent툴 워커 (최대 3 동시) | |
| 완료 처리 | 체크리스트 항목 `[x]` 갱신 | |
| 정리 | 명세/체크리스트 보존, 팀 해체 | |

# 주의 사항

- **명세 파일 작성 후 사용자 승인 없이 절대 실행에 들어가지 않습니다.** 작업 분해가 잘못되면 추후 수정이 어렵습니다.
- 동시 워커 수는 **최대 3개**를 넘지 않습니다.
- `dependencies`가 있는 작업은 의존 작업이 모두 `[x]`가 된 이후에만 spawn/할당합니다.
- 워커는 결과를 반환할 때 완료된 작업 식별자(`Task1` 등)를 명확히 포함해야 합니다.
- 동일한 `{프로젝트명}_{작업명}` 파일이 이미 존재한다면 사용자에게 덮어쓸지/다른 이름을 쓸지 확인합니다.
